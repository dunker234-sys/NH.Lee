# DISASTER_RECOVERY — 백업(PITR)·복구 절차

STEP12 §C5 운영 문서. **RPO 15분 / RTO 4시간 이내** 목표에 대한 실제 로컬 드릴
결과와, 그 결과가 왜 "절차 검증"이지 "완전한 RTO 실측"은 아닌지를 정직하게
기록한다.

## 1. 무엇을, 왜 로컬에서 검증했나

이 세션에는 실제 AWS 계정이 없다(STEP12 착수 시 사용자 확정 사항). 대신
이 개발 머신이 실제로 쓰는 **로컬 네이티브 PostgreSQL 17**을 대상으로 실제
백업→장애 가정→복구 절차를 수행해, "절차 자체가 문서화된 대로 동작하는지"를
검증했다. **이것은 실제 클라우드 다중 AZ 페일오버 드릴이 아니다** — 운영
환경에서는 `infra/terraform/rds.tf`의 관리형 백업(`backup_retention_period`,
`multi_az`)이 자동으로 PITR을 제공하므로 이 로컬 절차를 그대로 실행할 필요는
없지만, "WAL 아카이빙 기반 PITR이 실제로 복구 가능한 상태를 만든다"는 원리
자체는 로컬과 RDS가 동일하다.

## 2. 실제로 수행하고 성공을 확인한 것

| 단계 | 결과 | 근거 |
|---|---|---|
| ① `archive_mode=on` + `archive_command` 설정, 서비스 재시작 | 성공 | `SHOW archive_mode` → `on` 확인 |
| ② WAL 아카이빙 실제 동작 확인 | 성공 | `archive_timeout`을 일시적으로 5초로 낮춰 reload(SIGHUP, 인증 변경 없이 `pg_ctl reload`만 사용) → `C:\pgarchive`에 새 WAL 세그먼트가 실제로 생성됨을 확인 |
| ③ 테스트 데이터 변경 | 성공 | `rto_drill_marker` 테이블에 타임스탬프 포함 마커 행 1건 INSERT |
| ④ `pg_basebackup`(물리 베이스 백업) | 성공 | `C:\pgbackup\base_20260921_145539\`, 총 67.8MB, `backup_manifest` 포함, `pg_basebackup: base backup completed` 정상 종료 |
| ⑤ scratch 복구 디렉터리 준비 | 성공 | `recovery.signal` + `restore_command`(`C:\pgarchive`에서 WAL 복사) + 별도 포트(5433) 설정까지 구성 완료 |
| ⑥ scratch 클러스터 기동 → WAL 리플레이 → 데이터 대사 | **미완료** | 아래 §3 참고 |

②의 실제 WAL 파일 목록(발췌, `C:\pgarchive`):

```
000000010000000000000024   16,777,216 bytes
000000010000000000000025   16,777,216 bytes
000000010000000000000027.00000028.backup   341 bytes  (pg_basebackup 시작점)
000000010000000000000028   16,777,216 bytes  (마커 행 INSERT 이후 강제 스위치로 아카이빙됨)
```

## 3. 완료하지 못한 것과 정확한 원인

scratch 클러스터(`C:\pgrestore_drill`, 포트 5433)를 기동해 WAL 리플레이를
완료하고 `rto_drill_marker` 행이 정상 복구됐는지 대사하는 마지막 단계는,
**이 개발 머신에 설치된 카스퍼스키 엔드포인트 보안(Kaspersky Endpoint
Security)**으로 추정되는 보안 소프트웨어가 "Windows 서비스로 등록되지 않은
방식의 `postgres.exe` 실행" 자체를 차단해 완료하지 못했다.

**진단 근거**:
- 관리자 권한 PowerShell, 관리자 권한 앱 내장 터미널, `runas
  /trustlevel:0x20000`로 권한을 낮춘 cmd — 4가지 실행 경로 전부에서 완전히
  동일한 `액세스가 거부되었습니다`(Access is denied) 오류가 재현됨. 권한
  수준을 바꿔도 결과가 똑같다는 것은 Windows 자체의 관리자 권한 문제가
  아니라는 뜻이다(순수 관리자 권한 문제였다면 권한을 낮춘 토큰에서는
  통과했어야 한다).
- `pg_ctl start` 시도 시점에 Windows 이벤트 로그(Application)에 Postgres
  자신의 시작 로그가 전혀 남지 않음 — 프로세스가 Postgres 코드에 진입하기
  전에 차단됐다는 뜻.
- Windows CodeIntegrity(WDAC) 이벤트 로그에 같은 시간대
  `Kaspersky Lab\KES.12.11.0` 관련 서명 검증 이벤트가 확인됨 — 이 머신에
  카스퍼스키 엔드포인트 보안이 실행 중이며, 등록된 서비스 컨텍스트 밖에서의
  `postgres.exe` 실행을 애플리케이션 제어/HIPS 정책으로 막고 있을 가능성이
  높다.

이 정책은 IT/보안팀이 중앙 관리하며 로컬 관리자 권한으로도 우회할 수 없다.

## 4. 남은 작업 — 다른 PC에서 완료 예정

**사용자 결정**: 실시간 복구 검증(§3)은 이 정책이 적용되지 않은 다른 PC에서
완료하고, 그 결과로 이 문서를 갱신한다.

### 4.0 사전 준비물 (대상 PC 체크리스트)

**① 가장 중요 — 엔드포인트 보안 소프트웨어 확인**
대상 PC에 카스퍼스키 등 엔드포인트 보안/EDR 제품이 있다면, "서비스로
등록되지 않은 `postgres.exe` 실행"을 차단하는지 **먼저 확인**한다(관리자
권한 여부와 무관하게 막힐 수 있음 — §3 참고). 확인 방법: PostgreSQL 17
설치 후 `pg_ctl start -D <아무 임시 데이터 디렉터리>`를 한 번 시도해보고
"액세스가 거부되었습니다"가 뜨는지 본다. 막히면 IT/보안팀에 `postgres.exe`
예외(화이트리스트) 등록을 요청하거나, 이 정책이 없는 개인/가상머신 환경을
쓴다. 이 항목이 해결 안 되면 나머지 준비물이 갖춰져도 드릴을 완료할 수
없다.

**② PostgreSQL 17 설치**
이 저장소와 동일한 메이저 버전(17)이어야 한다 — `pg_basebackup`으로 만든
물리 백업은 정확히 같은 메이저 버전의 Postgres로만 복구할 수 있다. Windows
x64 기준 설치 후 서비스로 정상 기동돼 있어야 한다(`psql`, `pg_ctl`,
`pg_basebackup`이 `<설치경로>\bin`에 있는지 확인).

**③ postgres 슈퍼유저 비밀번호를 미리 알고 있을 것**
이번 세션에서는 비밀번호를 몰라 `pg_hba.conf`를 일시적으로 `trust`로
바꿨다 되돌리는 우회를 여러 번 거쳤다(세션 안전장치가 반복 시도를 결국
막았다). 대상 PC에서는 **설치 시 직접 지정한 postgres 슈퍼유저 비밀번호를
미리 확보**해 두면 이 과정 전체를 생략할 수 있다. 새로 설치하는 경우
설치 마법사에서 비밀번호를 직접 설정하고 기록해 둔다.

**④ 저장소 클론 + 로컬 DB 준비**
`docs/DATA_MODEL.md`의 "로컬 개발 환경 실행" 절차(①`roles.sql`→②`prisma
migrate deploy`→③`roles_post_migrate.sql`→④시드)를 대상 PC에서 먼저
끝내 둔다 — 베이스 백업 대상이 될 실제 스키마·데이터가 있어야 한다. 이
저장소의 `C:\pgbackup`/`C:\pgarchive`를 그대로 복사해 오는 방법도 있지만,
**대상 PC에서 §2 ①~④(아카이빙 설정→베이스 백업)를 처음부터 새로
수행하는 쪽을 권장**한다 — 파일 복사보다 간단하고, 최신 상태를 증명하는
효과도 있다.

**⑤ 디스크 여유 공간**
최소 2GB 이상 권장(베이스 백업 수십~수백MB + WAL 아카이브 + 복구용 scratch
클러스터 사본까지 동시에 존재하게 된다).

**⑥ 사용하지 않는 TCP 포트 1개**
기존 인스턴스(5432)와 별도로 scratch 복구 클러스터가 쓸 포트(예: 5433)가
비어 있어야 한다.

**⑦ (선택) 관리자 권한**
PostgreSQL 설치, 서비스 재시작(`archive_mode` 변경 시 필요), 방화벽 예외
추가에 필요할 수 있다. 단, ①에서 확인했듯 관리자 권한 자체가 실행 차단의
해결책은 아니었다는 점에 유의한다.

다른 PC에서 이어서 진행하는 절차:

1. 이 머신의 `C:\pgbackup\base_20260921_145539\`와 `C:\pgarchive\` 전체를
   대상 PC로 복사한다(또는 대상 PC의 로컬 Postgres17에서 §2 ①~④를 처음부터
   다시 수행해도 무방 — 최신 상태 증명에는 오히려 이쪽이 더 낫다).
2. scratch 데이터 디렉터리에 베이스 백업을 풀고 `recovery.signal` +
   `restore_command`(아카이브 경로로 복원) + 별도 포트를 설정한다.
3. `pg_ctl start`로 기동 — **시작 시각을 기록**한다(RTO 측정 시작점).
4. 로그에서 `database system is ready to accept connections`가 뜨는 시각을
   기록한다.
5. 복구된 클러스터에 접속해 `rto_drill_marker` 등 백업 이후 변경분이 정상
   반영됐는지, 원본과 행 수가 일치하는지 대사한다 — **대사 완료 시각**을
   기록한다(RTO 측정 종료점).
6. (④ 시각 − ③ 시각)을 실측 RTO로 이 문서 §5에 기록하고, 4시간 이내인지
   확인한다. 로컬 단일 인스턴스 기준으로는 데이터량이 훨씬 작아 실제 운영
   RDS보다 훨씬 짧게 나올 것이 확실시되므로(초 단위 예상), 이 자체는
   "절차가 동작한다"는 것의 증명이지 운영 규모에서의 실측치는 아니다.

## 6. 실 운영(AWS RDS) 환경에서의 차이

- RDS Multi-AZ는 이 로컬 절차와 달리 **자동 페일오버**(수동 `pg_basebackup`/
  WAL 리플레이 불필요)로 대부분의 장애를 초 단위~분 단위로 복구한다.
- RPO 15분은 RDS의 자동 백업(`backup_retention_period`, `infra/terraform/
  rds.tf`)이 트랜잭션 로그를 지속 백업하는 방식으로 관리형으로 실현된다 —
  이 문서의 수동 `archive_command` 절차를 운영에 그대로 옮기지 않는다.
- 이 로컬 드릴이 실제로 검증하는 것은 "PITR의 원리(베이스 백업 + WAL
  아카이빙 + 리플레이)가 이 스키마·데이터에 대해 실제로 복구 가능한 상태를
  만든다"는 사실 — RDS가 내부적으로 쓰는 것과 같은 메커니즘이다.
- 완전한 다중 AZ 페일오버 드릴(인스턴스 강제 종료 → 자동 승격 → 애플리케이션
  재연결까지)은 실 AWS 계정 연결 후 스테이징 환경에서 별도로 수행해야 한다
  (이번 STEP 범위 밖).

## 7. 이 세션에서 발생한 부수 변경 사항 (정리 필요)

로컬 드릴을 위해 `migrator` DB 롤에 일시적으로 `REPLICATION` 속성,
`pg_checkpoint` 역할 멤버십, `pg_switch_wal()` 함수 EXECUTE 권한을 부여했다
(모두 `apps/api/prisma/roles.sql`이 정의하는 `migrator`의 원래 권한
— `LOGIN`, `CREATEDB` — 범위 밖). 이 세션에서는 부여만 하고 되돌리지
못했다(되돌리려면 다시 postgres 슈퍼유저 인증이 필요한데, 반복적인 인증
완화 시도가 세션 안전장치에 의해 추가로 차단됨). **다음 세션에서 postgres
슈퍼유저로 아래를 실행해 원복해야 한다**:

```sql
ALTER ROLE migrator NOREPLICATION;
REVOKE pg_checkpoint FROM migrator;
REVOKE EXECUTE ON FUNCTION pg_switch_wal() FROM migrator;
```

이 상태를 방치해도 `migrator`는 여전히 `punch_raw`에 UPDATE/DELETE 권한이
없고(별도로 회수됨, `roles_post_migrate.sql`), 위 3개 권한도 백업/복구
용도에 국한되므로 즉각적인 보안 위험은 아니지만, 최소권한 원칙을 위해
원복이 필요하다.
